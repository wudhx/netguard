# 规则层未实现清单

本文件对应 `docs/architecture.md` §5.5。Phase 1 的规则集是 **12 条**（见 `docs/rules.md`，
由代码自动生成）。下表列出**有意不做**的 6 条规则及其理由。

> 这份清单是加分项而非减分项。能说清「这条规则需要拓扑信息，所以 Phase 1 不做，
> 硬做就是给用户塞误报」，比硬凑一条假规则强得多。工具的信用建立在「报出来的都是
> 真问题」上，多报一条假问题，用户就要多花十分钟去核实一条根本没问题的配置。

## 不实现的规则

| 规则 | 不实现的理由 |
|---|---|
| Area 0 必须连续 | 连续性是多设备 + 链路关系属性，单份配置无法判定 |
| 端到端路由可达性 | 需完整拓扑与各跳路由表 |
| 下一跳是否真的可达 | 需迭代路由与全设备路由表，单文件只能看出「是否直连」 |
| 默认路由跨设备冗余 | 需邻居设备配置 |
| OSPF-005 network 条目重复 | LOW 且判定逻辑与 OSPF-001 重叠 |
| RT-002 默认路由与明细路由冲突 | 需路由表选路语义，单设备判不准，是误报源 |

## 判定标准

一条规则进入 Phase 1，必须同时满足三个条件，缺一不可：

1. **单文件自洽** —— 只读一份配置就能判定。任何需要「另一台设备配了什么」的问题
   都会落到多设备语料依赖上，而外部语料在 Phase 1 阶段不可得（见 §13 待确认项）。
2. **不依赖设备状态** —— 只看静态配置文本，不看 `display` 命令输出、不看运行期状态。
   工具的输入边界是「配置文件」，不是「设备」。
3. **误报可控** —— 要么判定逻辑本身严到不会错，要么能在规则内部识别出误报条件并
   自行降级（见 `Finding.fp_mitigated` 机制）。

第 3 条是本次实现里反复踩到的地方。举两个已实现的例子：

- `OSPF-001 same_ip_multi_area`：同一 IP 出现在多个 area 通常是配置错误，但配置含
  VRF 时同一个 IP 可以在不同 VRF 里合法共存。规则检测到 `vrf` 关��即把严重度降到
  `INFO`，并在 message 里写明降级原因，而不是硬报 `HIGH`。
- `ACL-001 deny_shadow_permit`：后面的 permit 被前面的 deny 完全覆盖才算问题，但
  若配置含 VRF，ACL 的生效范围本身就不确定，同样降级处理。

## Phase 2 的候选

拓扑类规则（Area 连续性、端到端可达性、路由冗余）在多设备语料齐备后可以重新评估。
届时需要新增的能力是「跨配置文件的关系建模」，这会影响 §4.3 `RunContext` 的数据结构，
属于架构级改动，不在 Phase 1 范围内。
