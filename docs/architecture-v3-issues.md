## 1. `empty_streak` 会在正常配置上误判为"无新信息"

**位置**：V3 §6.2 `run_turn`

**现象**

```python
progressed |= result.added_count > 0
empty_streak = 0 if progressed else empty_streak + 1
if empty_streak >= MAX_EMPTY_STEPS:
    return degrade_turn(ctx, reason="no_new_info")
```

`progressed` 的唯一来源是"新增 finding 数 > 0"。但在一台**配置本身没有问题**的设备上，每条规则都返回 0 条 finding，这是完全正常的结果。

**影响**

- 连续执行两条规则且均未命中 → `empty_streak` 达到阈值 → 提前降级为 `no_new_info`；
- 候选集中其余规则一条都没执行，但报告仍按正常形态产出，**表面成功、实际只覆盖了极少数规则**；
- 该行为直接命中 V3 §8.2 自述的结论"Agent 走错路，结果不会错，只会漏"——本缺陷使"漏"成为系统性而非偶发；
- 触发条件是最常见场景（健康配置），不是边界场景。

**待澄清**："无新信息"的判定对象是"新增 finding"还是"重复的调用行为"？二者在健康配置上结论相反。

## 2. `ctx.findings` 以 `rule_id@location` 为键会覆盖丢失

**位置**：V2.0 §5.2 `RunContext.findings: dict[str, Finding]`（V3 §1 声明原样保留），V3 §4.2 的校验逻辑依赖该键

**现象**

同一规则在同一位置上可能产生多条不同结论（例如接口网段重叠类规则，一个接口对多个对象命中，`location` 相同而 `message`/`evidence` 不同）。以 `f"{rule_id}@{location}"` 为字典键时，后写记录覆盖先写记录。

**影响**

- findings 数量静默减少，报告漏项，且不留任何痕迹；
- `verify_claims` 以同一键查表，无法区分"该位置有一条断言"与"该位置本应有 N 条"；
- 报告覆盖率（V3 §5.3）的分母随之失真。

**待澄清**：findings 的唯一性维度是 `(rule_id, location)` 还是需要引入第三个区分项？

## 3. `verify_claims` 的指标名与实际校验对象不符

**位置**：V3 §4.2（校验逻辑）、§5.2（指标定义）

**现象**

V3 §4.2 的校验是纯查表：

```python
key = f"{c['rule_id']}@{c['location']}"
supported = key in ctx.findings
```

即：只校验 claim 的**定位字段**能否命中 findings；`text` 字段（自然语言表述）为自由文本，不参与任何机械比对。而 §5.2 把该指标命名为"无依据表述率"，语义指向"表述是否有依据"。

**影响**

- 一个正确的 `rule_id@location` 可以搭配一句错误的 `text`（例如引用正确的规则与位置，但把"permit 被 deny 覆盖"写成"permit 缺失"），查表通过，指标记为 0 违规；
- 指标名承诺的"反向论证"（这条表述是否有依据）与实际测量的"引用有效性"（这条引用是否指向已有发现）不一致；
- 该指标是对外报数与面试答辩的核心数字，口径错位会在被追问时直接暴露。

**待澄清**：报告正文中"事实陈述"部分由模型撰写还是由 `core` 输出？该指标应命名为"引用有效率"还是另有口径？

## 4. 规则总数口径三处互相矛盾

**位置**：V3 §3.4、§7.1

**现象**，同一小节内出现三种说法：

| 出处          | 说法                           |
| ----------- | ---------------------------- |
| V3 §3.4 正文  | "把动作空间从 **20+** 收敛到 5—9 条"   |
| V3 §3.4 代码块 | "全部规则 **12 条** ↓ 候选规则 5—9 条" |
| V3 §3.4 结尾  | "选择空间是 9 选 N，不是 **20** 选 N"  |
| V3 §7.1     | "明确交付 **12** 条"              |

**影响**

- 若全部规则为 12 条，则候选集 5—9 条意味着过滤最多只剔除 7 条、最少仅剔除 3 条；" Agent 在候选内决策"的实际选择空间很窄，M1（规则选择）作为承重机制的论证强度不足；
- V2.0 §6.2 的画像预过滤以"20+ 收敛到 5—9"为前提，与 12 条总量不兼容；
- README 与指标（规则选择召回率）的分母无法确定，报数口径不成立。

**待澄清**：规则清单的总数是 12 还是 20？"清单总数"与"W4 交付数"是否为两个不同口径？

## 5. 分层维度无法表达"结论确定但需人工确认意图"这一档

**位置**：V2.0 §5.3 `@rule(needs=...)`（V3 §1 声明原样保留）

**现象**

`needs` 取值 `SINGLE_DEVICE / MULTI_DEVICE / TOPOLOGY`，描述的是"判定需要什么输入"。但规则库中存在第三类规则：单设备配置即可确定，结论也不依赖拓扑，但**是否算问题取决于运维意图**——例如"物理接口缺少描述""接入侧未配置 silent-interface""ACL 缺少显式拒绝"。

这类规则：

- 满足 `needs=SINGLE_DEVICE`，会被当作确定性结论计入指标；
- 但实际只是规范建议，计入 Precision/Recall 会污染口径。

**影响**

- 指标层无法区分"确定性缺陷"与"规范建议"，规则层 Precision 的定义不成立；
- 报告层无法据此决定排序与措辞（前者应报"错误"，后者应报"建议"）；
- `applies_to` 与 `needs` 是两个正交维度（相关性 / 输入依赖），现有规格只有一个。

**待澄清**：分层维度是几维？"需人工确认意图"这一档在数据模型中如何表达？

## 6. `applies_to` 引用的 `Role` 枚举从未定义

**位置**：V2.0 §5.3 `applies_to={Role.CORE, Role.AGG, Role.BORDER, Role.ACCESS}`，V2.0 §4.2 `core/profile.py`（设备画像）

**现象**

`Role` 的取值集合、每个取值的判定条件、以及"判不出角色"时的行为，全文均未定义。

**影响**

- `core/profile.py` 无法实现：它要输出"候选规则集"，但候选集由 `applies_to` 过滤，而 `Role` 无从计算；
- V3 §3.4 与 §6.2 的 M1 全链路（画像 → 过滤 → 候选集 → Agent 选择）缺少第一环；
- 无兜底规则时，一份角色特征不明显的配置可能得到空候选集，Agent 将无规则可跑，且该情形未被任何降级分支覆盖。

**待澄清**：`Role` 枚举有哪几个值？判定条件是什么？判定失败时的兜底行为是什么？

## 7. 交付物为增量补丁，无法独立执行

**位置**：V3 全文体例

**现象**

V3 开头声明"本版是 V2.0 的修订版，**不重写全文**。V2.0 未在本版提及的章节，原文有效"，并在 §1 列出保留章节清单、§10 列出差异汇总。

**影响**

- 实施方必须同时持有两份文档并在阅读时自行合并，任何一处遗漏都直接变成实现错误；
- 该风险已有先例：V3 §0.1 自述"第 1 轮修订版在只读了 V2.0 前 2KB 的情况下动笔，误砍了原文档的核心设计"——一份需要"合并阅读"的文档，读漏是必然事件而非偶发失误；
- §1 保留清单与 §10 差异表存在覆盖边界：未被任何一处提及的章节，其有效性无判定依据。

**待澄清**：交付给实施方的最终物是"V2.0 + V3 两份"还是"合并后的单一文档"？
